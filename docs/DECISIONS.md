# Decisions

Required baseline decisions were delegated by the user on 18 November 2026. New novelty proposals remain open.

1. **Data boundaries.** Use all 80 training trips with trip-grouped CV and 10 student-test trips for development. The initial package omitted evaluator trips. Development mode must be labelled; evaluator mode requires a separate folder of ten reserved trips and never substitutes development data. Later, `evaluator_test.zip` arrived: the predictor/scorer was frozen in commit a61ce50 before archive access, then all ten trips underwent final evaluation. Their results may not select or change any setting.
2. **Reference alignment.** Derive pointwise proxy labels by minimum-cost monotone alignment along the ordered reference arc sequence. This handles route revisits without treating route row number as GPS row number. It assumes chronological route order and uses squared point-to-segment distance. Exclude labels farther than 75 m only from fitting, report the excluded count, and score all observations. This is an imperfect supervision convention, not official pointwise ground truth. Also report direct length-weighted reference-route overlap and ordered sequence agreement. The user explicitly delegated this alignment choice after being told labels are missing.
3. **Portable geometry.** Use a per-trip local equirectangular projection in metres, with latitude-dependent longitude scale. Index samples along every directed edge at at most 30 m spacing, then compute exact segment projections. Candidate lookup must not depend on reference routes. Record geographic extents; this approximation is for local trip networks, not global distances.
4. **Binary candidate learning.** Predict whether an observation/candidate pair matches its proxy reference arc. Arc IDs are trip-local metadata, never categorical model inputs. Fit five distinct algorithms, choose by mean grouped-CV candidate Macro F1, and retain Top-1 and route metrics to reveal mismatch between classification and route quality. Fit scalers inside each fold.
5. **Bounded experiments.** Train on every fifth GPS observation in every training trip; evaluate every student-test observation. Use three identical trip folds, seed 357, and 12 sequential Optuna TPE trials (four startup trials, eight adaptive trials). Avoid random validation splits inside boosting. Preserve every measured model and trial. CPU baselines avoid remote compute setup latency; Kaggle remains an option if justified by measured need.
6. **Directed route decoding.** Hidden states are projected directed candidate arcs. Normalised classifier positive scores provide emission potentials. Directed shortest-path distance, including partial candidate-edge lengths, supplies transition compatibility. Use log-space Viterbi and reset at >60 s gaps or when no path remains. Return explicit breaks and route bridges rather than drawing impossible straight links. This discriminative-emission HMM-style decoder is inspired by Newson & Krumm, not a claim of novel HMM methodology.
7. **Deployment.** This Linux laptop hosts FastAPI; Chiranth's Mac serves the static UI. Requests contain only trip IDs. The server reads input files, predicts, then separately reads reference routes for scoring. No reference arc IDs or reference geometry enter evaluator responses or maps. Development report maps may display reference geometry.

8. **Measured decoder choice and reconstruction correction.** A recorded six-setting development comparison selected beta=25 m with globally scaled exponential transition potentials, rather than row-normalising a truncated candidate lattice. Final reconstruction must preserve an actual directed loop when successive projections lie on the same arc but move backwards by more than the fixed 3 m jitter allowance. A regression test verifies that loop; this correction occurred before evaluator access. Final development route-overlap F1 is 0.9570 after including those traversals, superseding the earlier incomplete-bridge figure of 0.9648. Pointwise predictions did not change.

9. **Read-only trace endpoints for the UI (after reserved evaluation).** `pathsnap/trace.py` serialises an already finished `Prediction` (GPS, decoded route geometry, per-point candidates, probabilities and Viterbi picks). `api.py` adds `GET /trace/{id}` and `GET /explain/{id}/{i}`; the latter recomputes the decoder's transition term into one point with the same `transition_distances` call and `-|route - GPS| / beta` formula. Neither reads references or changes candidates, scores, decoder settings or outputs; a test checks the trace's Viterbi picks equal `predicted_arc_ids`. This changes `api.py`'s hash relative to `evaluation_freeze.json`; every predictor file (pipeline, features, decoder, geometry, model, config) still matches. Reserved results were not re-run or used.

10. **Single consolidated submission report generated from artifacts (19 November 2026).** `scripts/build_final_report.py` (with `scripts/final_report/` and `scripts/report_figures.py`) writes `reports/PathSnap_Final_Report.pdf` from committed `artifacts/` files only, following the Deliverables numbering and answering every listed question, with a traceability appendix for all five organiser PDFs and SHA-256 hashes of every source artifact. It needs no raw data and changes no predictor file. Missing evidence (receiving-terminal screenshot, current UI captures) is shown as a marked placeholder and inserted automatically when the genuine file is saved in `reports/evidence/`. The earlier 18-page report moved to `reports/archive/`; the deck and viva study guide moved to `reports/supporting/` so only one submission PDF sits in `reports/`.

Open: Bhuvan's novelty; any organiser-specified per-point scoring convention; genuine two-device demo evidence. The supplied reserved package was evaluated after freeze without further tuning. No novelty claim is made for the required baseline.
